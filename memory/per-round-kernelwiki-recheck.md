Phase 2/3 的每一轮，NCU 定位出主瓶颈后**必须给出本轮方向的可审计依据**，写进该 kernel `PROGRESS.md`
本轮日志的**「本轮方向依据」必填字段**。依据**二选一、地位对等**：
- 【KernelWiki 命中】查了哪些页（列路径）→ 每张页一句「手法 + 其前提在本 kernel 成立/不成立」→ 采纳/拒绝理由；
- 【自研分析】当 KernelWiki 无迁移性好的方案时：一句说清扫过哪页/为何不适用（前提 A vs 本 kernel B）
  → 从「本轮 NCU 具体指标名+数值」到「瓶颈机制」到「所以改 X」的**因果链** + **量化预测**（下一轮回填实测）。

**关键定位（2026-08-06 用户明确）：KernelWiki 是可参考的首选来源，不是必经收费站。** 当其方案迁移性不好
或没有可用方案时，应发挥自己的经验直接分析 NCU 推导方向，不要局限在 KernelWiki 里。旧版「每轮必须回查/
命中 KernelWiki」的打卡式硬约束已废除——它会把"洞察驱动"降级成"检索驱动"，压制自研发挥。
两条路都必须落到**本轮**具体瓶颈（指标名+数值）；字段为空 / 写「同上轮 / 已在 Phase 1 查过」/ 沿用开局
静态方向清单 = 本轮未完成，不得进 review。

**防「假自研」滑坡（核心设计，务必守住）：** 把自研设成对等路径后最大的风险是每轮都写「wiki 没方案，我自己分析」
来躲开翻 wiki。反敷衍靠的不是「必须命中 wiki」，而是**依据必须落到本轮具体数字 + 自研预测下一轮被复现验证**：
(1) 自研路径要求具体到本轮 NCU 指标名+数值的因果链——编一段像样的比瞄一眼 wiki 更累，捷径不成立；
(2) 量化预测 + 下一轮回填 + reviewer 独立复现数字，预测连续对不上就暴露是编的；
(3) 「为何不适用」要承重（前提 A vs B），照样要真瞄过页。诚实去 wiki 找（秒级）仍是最省力默认动作，
只有 wiki 真没方案时写自研才划算——躲不再省力，躲就自然消失。

**Why:** 2026-07-27 曾因 `fused_q_indexer_rope_hadamard_quant` 连漏八轮回查而收紧成硬约束；根因不是记不住，
是要求只写在散文里、没进每轮实际填的 PROGRESS.md 模板、被上下文压缩冲掉、reviewer 只查结果不查过程。
2026-08-06 用户指出收紧过度、变成了限制自身发挥的收费站，故改为「首选参考 + 对等自研路径 + 可证伪的真依据」。
教训仍成立：**要求必须放进每轮实际填写的那张表**（否则压缩后就没了），只是被审计的东西从"查没查 wiki"
换成"本轮方向有没有站得住、可证伪的真依据"。

**How to apply:** 已把新语义固化进（2026-08-06 全部落盘）：
`kernel-template/{PHASE_TEMPLATE.md,PROGRESS.md,CLAUDE.md}`（字段更名为「本轮方向依据」，两条对等路径）+
`skills/gen-kernel-phases/SKILL.md` Step 10（对所有新建 kernel 生效）+ `reviewer/CLAUDE.md` 审查第 5 步
（命中路径抽查页面引用真实性；自研路径查因果链具体性 + 预测回填，空话/预测对不上判 ISSUE）。
分工原则不变：**优化 agent 侧字段说明保持短**（每轮重读、会被压缩），**审查细节全放 `reviewer/CLAUDE.md`**
（隔离会话一次性读入，成本不累积）。即「短要求 + 严审查」。
环境坑：`query.py` 在本节点报 `No module named yaml`，须换 `/usr/local/bin/python`；不得因命令报错就跳过。
见 [[progress-md-round-log-ordering]]。
