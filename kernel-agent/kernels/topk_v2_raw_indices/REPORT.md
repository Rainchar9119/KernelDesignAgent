## 1. 一句话结论

对 `topk_transform_512_v2`（融合 top-k 选择 + page-table transform）做的优化只有**一件事**：
**host 侧按 (batch, seq_len) 自适应路由到 N∈{8,4,2} 路的 cluster split**，把超长序列切成 N 块交给
一个 cluster 的 N 个 block 并行处理，替掉 baseline 的「persistent pool 多波串行 / 单块 Streaming」。

- **不改 API、不改数值结果、不改 kernel 实现文件**（`topk_impl.cuh` 自始至终一行未改）。
- **收益区间**：`batch∈[31,76]` 且 `seq≥114688`。峰值 **0.61×（≈1.64× 加速）@ (b76, L262144)**。
  该区间外（batch≤30 / batch≥77 / seq≤98304）逐字回落 baseline，无收益也无退化。
- **正确性**：零容差（逐行 top-k 集合相等 vs `torch.topk`），内部 verify 196/196 + 官方单测 244 passed；
  开源侧 286 passed；两侧 `compute-sanitizer memcheck` 均 0 errors。
- **⚠ 已提交的内部 CR 存在一处未修的退化**：`b40 × L≥196608 = 1.10–1.13`（详见 §6）。修复方案已在
  开源分支验证有效且顺带把 b46–64 提升一大截，**尚未回移到内部**。

## 3. 优化做了什么

### 3.1 瓶颈（NCU 实测）

超长 seq × 小/中 batch 时，baseline v2 有两种都不划算的走法：

- **单块 Streaming**（`topk_main_kernel<1,3>`，grid = batch）：一行一个 block 流式扫完。b64/L131072 实测
  Waves/SM 仅 **0.21**（64 个 block 铺 152 个 SM），Occupancy 49.5%，大半 SM 空转。
- **persistent cluster pool 多波串行**（`topk_persistent_cluster_kernel`，grid = 30×8 = 240）：池子只有
  `kNumPersistentClusters = 30` 个 cluster，batch > 30 就要 `ceil(batch/30)` 波**串行**跑完。b76 需 3 波。

两者都不是带宽或算力受限（该区间 Memory 15–30% / Compute 17–33%），而是**并行度与波次结构**问题。

### 3.2 手段：adaptive N-way cluster split

把一行的 `seq_len` 切成 N 段，交给**一个 cluster 内的 N 个 block**并行处理：各 block 建自己的局部
直方图 → 经 DSMEM 做 all-reduce 得到全局直方图 → 定阈值 → 各自收集候选 → 归并输出。grid 从 `batch`
变成 `batch × N`，SM 填满且**一波做完**，换掉了「多波串行」或「单块扫全行」。

kernel 侧复用**已经存在且已验证**的 `topk_small_batch_kernel` 与 `TopKCluster<N>`（原本只有 N=8），
只把它们模板化成 `topk_small_batch_kernel<kPDL, kNumRanks>` / `TopKCluster<kNumRanks>`，N∈{2,4,8}。

### 3.3 为什么 N 要自适应：单波容纳量

B200 一波能同时驻留 `SM × occupancy = 152 × 2 = 304` 个 block。一个 N-way cluster 占 N 个 block，
所以**一波能装 `304/N` 个 cluster**：

| N | 一波容纳 batch | 协调开销 | 适用区 |
|---|---|---|---|
| 8 | 38 | 最大（8-rank DSMEM all-reduce + 2× cluster.sync） | 极小 batch，或 seq 极长值得摊 |
| 4 | 76 | 中 | 中 batch |
| 2 | 152 | 最小 | 较大 batch，或 seq 刚过门限 |

N 越小协调开销越小、单波 batch 上界越高，但每块要扫的数据越多。所以 N 必须随 (batch, seq) 选，
固定 N 一定在某片区间亏。这是整套优化唯一的核心判断。

### 3.4 路由规则

优先级 `split8 > split4 > split2`，互斥不重不漏，未命中则**逐字回落 baseline 分支**（这是"区间外零退化"
的代码依据，reviewer 每轮都核对过）。

| 分支 | 条件（B200 标定值） |
|---|---|
| `route_split8` | `batch ≤ 30`（恒真项，与 baseline 同）**或** `batch ≤ cap8(64) 且 seq ≥ 196608` |
| `route_split4` | `batch ∈ (cap8, cap4(74)] 且 seq ≥ 131072` |
| `route_split2` | `batch ∈ (30, cap2(76)] 且 seq ≥ 114688` |
| fallback | 其余：persistent pool + `topk_main_kernel<1,3>`，与 baseline 逐字相同 |

三个 seq 门限（196608 / 131072 / 114688）是实测 crossover：N 越小协调开销越小，能吃的 seq 下界越低。

### 3.5 设备自适应缩放

上面的 cap 是 B200 实测值，写死会在换卡时误路由（把 batch 推进半空的第二波）。故 cap 改为运行时缩放：

```
cap_N = kSmallBatchNCap × sm_count / kCalibSMCount(152)     // 随 SM 数缩放
min_seq_N = kSmallBatchNMinSeq × l2_bytes / kCalibL2Bytes    // 随 L2 缩放
cap4_eff = max(cap4, cap8)，cap2_eff = max(cap2, cap4)       // 下界护栏，防过缩
```

`sm_count` / `l2_bytes` 用 `static const` 只查一次设备属性（与库内 `rmsnorm.cuh` 同模式）。初版每次
launch 都查 `cudaDeviceGetAttribute`（~1μs），把 b64/L2048 这种微秒级短序列 kernel 拖慢 5%，加缓存后消除。
B200 上缩放公式精确恒等于原硬编码值（152/152 = 1），所以本报告全部数字对两版通用。

### 3.6 单波容量修复（**只在开源线，内部线未回移**）

首版把 8-way 的 batch 上限设成 `cap8 = 64`，但 §3.3 算出 8-way 一波只装 **38** 个 cluster
（304/8 = 38）。于是 `batch ∈ (38, 64]` 走 8-way 时被挤进**半空的第二波**——付了两波的时间只干了
一波多一点的活。强制四路径（8/4/2-way/pool）逐格实测确认：8-way 对 batch 36–48 几乎从不最优，
**crossover 精确 = 38**。

修复：新增 `kSmallBatch8WaveCap = kCalibSMCount × kOccupancy / kClusterSize`（=38，随设备缩放），
`route_split8` 的高 seq 上限从 `cap8(64)` 收到 `cap8_wave(38)`，腾出的 `batch ∈ (38, 64] & seq ≥ 196608`
由 `route_split4` 接住（它一波装 76，仍单波）。**净效果：只有这一段换了 N，其余路由不变。**

## 9. 边界、已知问题、对旧版报告的修正

### 9.1 有效性边界

- **只对 `batch ∈ [31,76] × seq ≥ 114688` 生效。** 其余全部逐字回落 baseline：无收益也无退化。
  这不是取样偏好，是路由的硬边界——`else` 分支与 baseline 代码逐字相同。
- **batch ≥ 77 完全没有收益。** 该区间的瓶颈已不是并行度而是 DRAM：b256/L131072 实测
  `dram__bytes_read.sum = 269 MB` vs working set 134 MB = **2.00×**，Memory 66.4% > Compute 45.6%。
  host 路由只能把同样的工作在 SM 之间重新摊，**减不了搬的字节数**，对这类瓶颈结构上无效。
- **换卡未实测。** 只有 B200 一台机器，§3.5 的缩放公式在 SM=152 上手算恒等、方向正确（小卡更保守），
  但 H100/A100 上的实际不退化只能靠公式与代码逻辑保证，**无实测背书**。
- **`sm_count` 用 `static const` 缓存**，单 GPU 进程内正确；多 device 混用场景需留意。

### 9.2 最大的未做项：kernel 内部一次也没改过

`topk_impl.cuh`（`TopKRegister` / `TopKStreaming` / 直方图 / 阈值 / tie 解析，即真正的算法实现）
**在全部 keep 轮里一个字节都没改过**。所有优化都在 host 路由层，复用已有 kernel。

因此 `batch ≥ 77` 那片 DRAM-bound 区间至今零收益，而它的收益上界是**实测出来的**：
`TopKStreaming::forward` 有两遍 `for_each_input`（Phase 1 建直方图、Phase 3 重扫收集），第二遍在数据
超过 L2 时回 DRAM，这就是 2.00×。一个跳过第二遍的零成本 probe（输出故意错、只计时）实测
**b256/L131072 61.7→37.2μs = 0.60×，b256/L262144 102.6→57.7μs = 0.56×**。

当时给出的否决理由是「有界单趟不可实现」：阈值在 Phase 1 时未知，近阈值候选数轻易超过固定缓冲
`kMaxNumTie = 2048`，溢出即漏选、直接踩零容差。这个论证只证明了**朴素单趟**不行，不能证明没有有界
方案（例如 provisional-threshold + 缓冲满时压缩：丢弃的元素严格低于一个"上方已有 ≥ k 个元素"的阈值，
top-k 集合精确不变）。**这条路没有写过任何代码，属于未尝试，不是已证否。**

顺带一个应当独立处理的隐患：现有 verify 的数据生成是纯 `torch.randn`（`verify/verify_v2_raw_indices.py:88`），
连续分布下精确相等概率≈0，因此 **`kMaxNumTie` 溢出路径、整套 tie 解析、fp16 粗直方图 bin 边界、NaN
饱和逻辑从未被任何测试触发过**。也就是说 196/196 PASS 对涉及这些代码的改动几乎没有证伪能力。
